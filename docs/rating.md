# Rating 系统

作者：FubukiHanasaki。插件版本保持 0.2.0。

## 模块边界与算法升级

- `src/rating-core.ts`：独立计算模块。难度区间、初始分、种子排名、反解目标分、防膨胀修正、得分表现拟合、难度错配、新人系数、分数上限、称号、近 30 天变化分类。只依赖 JavaScript 标准库；没有 Hydro、MongoDB、网络和系统时间依赖。不会修改传入的参赛列表或状态。
- `src/rating-engine.ts`：`RatingEngine` 接口和默认 `legacySmsRatingEngine`。输入为参赛成绩、只读用户状态、难度和是否按罚时打破同分；输出为每人的前后分数、涨跌、排名、人数、有效系数和累计参赛次数。
- `src/rating.ts`：鉴权、历史记录导入、按时间重放、分数投影、不可变数据批次、排行榜和历史接口。通过构造参数注入引擎，不承担公式计算。
- `src/rating-hydro.ts`：将 Hydro 官方比赛成绩表转换成引擎输入，适配原版排行榜、主页榜单、用户名徽章、原版 RP 定时任务与比赛事件。
- `public/sms-addon/rating.js` / `rating.css`：页面、分段色带历史曲线、悬停／触屏／键盘详情、导入预览与比赛设置。`profile.js` 只管理用户资料页的即时标签切换，支持方向键和地址哈希恢复，不调用 Hydro 的滑动控制器。

升级时实现一个新的 `RatingEngine`，为其设置新的 `id`，再传入 `RatingService` 的第五个参数。引擎 ID 是算法实现标识，不是插件版本号；插件版本仍仅在用户要求时更改。结算结果的头记录保存引擎 ID；配置中存在比赛时，后续重算会在引擎 ID 改变后重放，即使比赛输入未变。运行时统一切换新引擎后，调用重新结算；不要混用不同引擎的工作进程。

计算结果由调用者应用：

```ts
const changes = legacySmsRatingEngine.calculate(participants, states, 'CSP-J', false);
for (const change of changes) {
  states.set(change.uid, { rating: change.after, contests: change.contests });
}
```

移植依据为旧系统 `handlers/rating_core.py`、`handlers/rating_analytics.py` 和 `static/elo_recent.html` / `student_profile.html`。独立测试使用旧 Python + SQLite 回放生成 120 组对照样本，覆盖多场比赛、不同难度、缺席、同分、罚时、显式名次、新人与老选手。包括 Python 的二进制浮点数舍入行为；测试脚本和对照数据统一放在被 Git 忽略的 `.tmp/`。

## 计算规则

每场比赛先读取官方成绩排名。首次参赛的起点按难度分别为 900、1400、1600、1700、1800。根据选手旧分与其他选手旧分计算期望名次，以实际名次和期望名次的几何平均反求目标分，取目标分与旧分之差的一半并向零取整。

随后按旧系统顺序执行：全局防膨胀、前 `4 × round(sqrt(n))` 人修正、比赛难度与选手层级错配系数、基于名次正态分位和标准分的表现拟合、得分率目标、动态差距牵引、前六场系数（0.35 / 0.5 / 0.65 / 0.75 / 0.82 / 0.88）、低难度比赛禁止越级正增长、难度分数上限及零分下限。分数保留两位小数，前后分数即真实分数，不添加新人显示补偿。

| 难度 | 表现区间 | 单场正增长上限 |
| --- | --- | --- |
| 入门 | 1000–1299 | 1399 |
| CSP-J | 1300–1899 | 2100 |
| CSP-S | 1900–2499 | 2700 |
| NOIP | 2100–2699 | 2999 |
| 省选/NOI | 2700–3500 | 3600 |

称号：未评级；已评级后依次为 Newbie（低于 1200）、Pupil（1200）、Specialist（1400）、Expert（1600）、Ace Expert（1800）、Candidate Master（1900）、Master（2100）、Legendary Master（2300）、Grandmaster（2600）、Legendary Grandmaster（3000）。

近 30 天同时有正、负变化时显示“波动”；否则净变化 ≥ 8 为“进步”、≤ -8 为“退步”，其余为“持平”。总榜按当前 Rating、计分比赛数和用户名排序；进步榜先按近 30 天净变化排序。同分显示并列排名。

## 比赛接入

入口为 `/sms#exams`。初始化由插件管理员逐场确认过往比赛的 Rated 选择，保留选中的已发布比赛快照和所有历史导入检查点。取消已发布比赛的 Rated 会在明确确认后重算历史；选中但尚未结算的比赛仍需管理员核验。原生 `tdoc.rated` 只用于初始化建议，不直接触发新系统计分。

比赛元数据包含类型、参赛班级、难度、范围、来源与说明；日期、时长、赛制、题目与满分来自 Hydro。难度选项沿用入门、CSP-J、CSP-S、NOIP、省选/NOI。

Rated 是待核验的计分设置。支持 OI、IOI、严格 IOI 和 ACM/XCPC；作业及其他赛制不纳入。管理员在比赛结束且所有正式提交完成评测后预览官方成绩，确认核验才生成新的不可变 Rating 批次。预览绑定管理员、比赛配置版本、正式成绩版本及全站 Rating 版本，15 分钟过期；成绩、配置或 Rating 发生变化时返回 409，需要重新预览。核验权严格限定插件管理员，即使授予普通模块权限也不能绕过。

已发布的正式成绩快照不会因定时任务、重测、修改难度或比赛开关而自动改写。修改之后需要再次核验；将 Rated 改为 Unrated 后，也需管理员确认核验才移除旧快照的贡献。正式成绩评测或比赛编辑会增加结果版本并显示待核验，订正记录不会增加正式结果版本。已有历史快照保持有效，直到管理员明确确认替换或撤销。

没有提交的报名者、虚拟用户及不计排名的参赛者不计入。并列成绩使用 Hydro 官方排名；ACM 使用通过题数和总罚时。OI 得分率按总分 / 题目满分之和（未设权重时每题 100 分），ACM 按通过题数 / 总题数。记录时间采用比赛结束时间。

## 旧数据导入

入口：`/sms#rating` → 导入记录。接受 CSV 或 JSON，也可粘贴；每批 1–500 条，先预览再确认。管理员必须提供学生已绑定的 Hydro UID、分数和记录时间，不使用旧系统学生 ID。榜单身份按查看者的 SMS 学生/教师档案绑定判断：未绑定的只返回匿名「选手N」，隐藏真实 UID 和用户名，不允许通过身份筛选反查；查看他人历史和历史导出会被拒绝，本人历史保留。

```csv
uid,rating,recordedAt
5,1680,2026-10-01 18:00:00
6,1950.25,2026-10-02 18:00:00
```

```json
{
  "records": [
    { "uid": 5, "rating": 1680, "recordedAt": "2026-10-01T18:00:00+08:00" }
  ],
  "preview": true
}
```

接口：`POST /sms/api/rating/import`，使用 Hydro 登录会话，`Content-Type: application/json`、`X-SMS-Request: 1`，以及与目标站点一致的 `Origin`。先发送 `preview: true`，返回 `data.revision`、新增 / 重复数量和前 20 条预览。提交相同 `records`，移除 `preview` 并带上返回的 `revision` 即确认导入。子域路径为 `/d/<domainId>/sms/api/rating/import`，Rating 数据全站共用。

- 支持日期、北京时间日期时间或显式时区；统一保存为 UTC。拒绝无效日期、未来时间、非数值 / 负数分数、无账号或无学生档案的 UID。
- 同一 UID、同一时间、相同分数自动去重；不同分数返回 409，整批不写入。重复提交不会增加历史条数。
- 导入记录是绝对分数检查点。第一条检查点本身不产生虚构涨幅；之后的检查点变化为与上一条有效记录的差值。较早的比赛可以继续重放，但不能改写导入时提供的绝对分数。
- 旧数据没有历史参赛次数，无法精确恢复新手阶段。为避免后续比赛把迁移分数重置为首次参赛起点，计算中将首次导入视为已有一次参赛；后续随真实计分比赛递增。此为缺失信息下的明确迁移约定，算法本身保持旧系统规则。
- 页面“计分比赛”仅统计插件实际结算的比赛，不将导入记录虚构为比赛次数。
- 确认时若有其他写入发生，版本校验返回 409，需重新预览。

学生档案批量导入也支持可选的 `Rating`、`Rating结算时间` 两列，用于只迁入最后结算检查点。它复用同一鉴权、时间校验、去重及不可变批次发布流程，详见 [学生批量导入](student-import.md)。

## 数据一致性

`sms_rating_head`指向唯一有效批次；`sms_rating_sources`、`sms_rating_summaries`、`sms_rating_changes` 保存每批的输入、用户投影和完整历史。新批次全部写完后，以数据库锁和版本比较原子切换头记录。中途失败、进程中断或并发冲突不会发布半成品；旧数据和导入检查点始终保留。历史批次作为恢复依据保留，不直接覆盖 Hydro 原版 RP 持久字段。插件启用时，显示与原版 RP 定时任务均由新系统接管。

读接口：`GET /sms/api/rating/board?mode=all|recent&page=1&q=&grade=&school=&classId=`、`GET /sms/api/rating/users/<uid>?page=1`。当前域成员范围由 Hydro 子域路径确定；列表只发布账号公开标识、分数与排名。写接口另有 `POST /sms/api/rating/contests` 与 `POST /sms/api/rating/recalculate`，均限定插件管理员并执行同源校验。

排行榜支持按班级筛选：`classId` 使用“班级与子域”的子域 ID。班级选项直接来自共享管理名单，不依赖学生是否建档；只列出当前用户可访问的班级。总榜、进步榜和翻页均保留所选班级，数据概览也按筛选结果统计。

用户资料页的 Rating 位于“个人简介”，不再创建单独标签；已有个人简介内容保留。曲线参考 Codeforces 的等级背景色带、细折线与节点样式，分数区间和称号仍使用插件原有规则。简介、最近活动、题解和学生资料均即时切换，不使用横向滑动动画。

年级和学校筛选仅对当前操作者可读取的学生档案生效，避免通过筛选结果推断未授权资料。榜单、导出和原生排名页的当前域取自 Hydro 实际路由，查询参数不能替换当前域；显式班级筛选仍单独校验访问范围。

## 离线赛正式批次

与独立的 Hydro Offline Judge 插件同时使用时，比赛快照读取会检查
`offline_judge_contests` 中以 `<domainId>:<contestId>` 为键的正式批次。
存在批次且 `state` 不是 `complete` 时拒绝结算，包括正式记录尚未完整建立、
中断及待人工检查的情况。没有该集合或该场比赛没有离线批次时，原有流程不变。

受本版 SMS 模拟赛管理的比赛，可以预先设置 Rated；正式代码包全部评测完成后再由管理员核验发布。未接入该核验流程的旧版 SMS 仍需在导入前关闭计分。订正记录不关联正式比赛，
不会进入 Rating 比赛快照。仅登记参赛但没有提交代码的用户仍沿用本模块的无提交排除规则。
